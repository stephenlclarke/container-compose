# 0.13.0 to 0.14.0 performance optimizations and Apple handoff map

## Purpose

This is a conversation guide for discussing the 0.14.0 performance work with Apple engineers. It separates public pull requests against stock Apple repositories from merged support-fork work and from local Apple-shaped change series. A local branch is not described as an Apple pull request.

## Scope and method

The inventory covers the `0.13.0..0.14.0` Compose range and the exact dependency revisions selected by those tags. It includes explicit performance changes plus the named runtime features and safety work that enable them. It does not turn an incidental speed change in a correctness or release commit into a performance claim.

## Optimization inventory

### 1. Core runtime and virtualization efficiency

These are the best candidates for an Apple discussion because the source series already applies directly to stock Apple bases.

| Area | Changes introduced in the 0.14.0 dependency range | Evidence and Apple status |
| --- | --- | --- |
| Event-loop sizing and reuse | Reuse the helper event-loop group; use one event loop per Container helper, builder client, virtual machine, and Cloud Hypervisor client. | The Container and Containerization local Apple-shaped series above contain these changes. [container #142](https://github.com/stephenlclarke/container/pull/142) and [containerization #37](https://github.com/stephenlclarke/containerization/pull/37) are merged support-fork evidence, not Apple PRs. |
| Shorter critical sections and more parallel preparation | Prepare independent run, create, machine-creation, machine-boot, archive, kernel, image, disk-usage, and cleanup work outside global actor or service locks; serialize independent container lifecycles separately; take one network snapshot for validation. | Included in the 29-commit Container candidate and [container #142](https://github.com/stephenlclarke/container/pull/142). No submitted Apple PR. |
| Image, registry, archive, and storage work | Traverse manifests and export manifests concurrently; coalesce export-progress setup; reuse registry bearer tokens; calculate image and active usage concurrently; perform archive I/O and orphan cleanup concurrently. | Included across the Container and Containerization candidate series. The matched stack proof is [container #142](https://github.com/stephenlclarke/container/pull/142) and [containerization #37](https://github.com/stephenlclarke/containerization/pull/37). No submitted Apple PR. |
| Faster readiness and cancellation | Start boot `virtiofsd` concurrently, poll helper sockets and the guest agent sooner, and cancel obsolete helper-readiness and guest-agent-dial work. | Included in the 19-commit Containerization candidate and [containerization #37](https://github.com/stephenlclarke/containerization/pull/37). No submitted Apple PR. |
| Cached build context | Add an additive `LookupContext` RPC, verify a completed content-addressed cache entry, and omit the transfer body on a cache hit while retaining legacy sender compatibility. The Container client also skips the cached upload. | [builder-shim #12](https://github.com/stephenlclarke/container-builder-shim/pull/12) has the protocol and focused proof; its one-commit Apple-shaped branch is available locally but no Apple PR has been submitted. |

### 2. Multi-container startup scaling

These changes are especially relevant to Apple because they address the cost of VM-per-container startup, while preserving explicit concurrency and safety boundaries.

| Change | What changed | Available proof | Apple discussion status |
| --- | --- | --- | --- |
| Concurrent VM bootstrap | [container #143](https://github.com/stephenlclarke/container/pull/143) takes only state capture and final commit under the host-wide service lock; independent VM bootstrap effects run concurrently and are generation-fenced before commit. | In a seven-repetition, counterbalanced run, 10-service startup fell from 5.244s to 1.611s (69.3%) and 50-service startup from 25.742s to 16.411s (36.2%). One-service startup regressed from 0.908s to 1.031s. | No Apple PR. The existing handoff describes a former local candidate as `upstream/pr-container-lifecycle-locks`, but it is not a public Apple branch. |
| Bounded bootstrap admission | [container #145](https://github.com/stephenlclarke/container/pull/145) keeps non-bootstrap work concurrent but limits VM boot admission to the smaller of 15 and the active processor count using a FIFO, cancellation-safe limiter. | 50-service startup median fell from 16.411s to 8.542s (47.9%); P95 fell from 22.674s to 12.944s (42.9%); Docker-normalized median improved 45.9%. One-service improved 1.8%; 10-service changed by 1.0%. | No Apple PR. This is a high-value design conversation because the control policy is explicit and its saturation benefit was measured. |
| Pipelined private workloads | [containerization #46](https://github.com/stephenlclarke/containerization/pull/46) releases the pod state mutex while a workload with a proven private writable root starts; shared or unknown roots remain serialized. [container #165](https://github.com/stephenlclarke/container/pull/165) adds a weighted, cancellation-safe gate with at most four private block roots in flight. | Focused admission and recovery tests prove the private-root prerequisite and preserve serialization for unsafe cases. No standalone percentage was retained. | No Apple PR. Discuss as a guarded concurrency contract rather than a blanket parallel-start change. |
| Explicit shared VM | [container #146](https://github.com/stephenlclarke/container/pull/146), [containerization #42](https://github.com/stephenlclarke/containerization/pull/42), and [container #159](https://github.com/stephenlclarke/container/pull/159) add an opt-in shared-VM path and bridge support. | The implementation is explicitly experimental and does not claim equivalent isolation; it enables the later pipelined-start work. | No Apple PR. It aligns conceptually with the open [apple/container #1924](https://github.com/apple/container/issues/1924) discussion, which is an issue, not a handoff PR. |

### 3. Warm starts and memory efficiency

| Change | What changed | Available proof | Apple discussion status |
| --- | --- | --- | --- |
| Dedicated-container prewarming | [container #150](https://github.com/stephenlclarke/container/pull/150) starts an eligible built-in dedicated VM after durable create, without starting init, then consumes the prepared runtime on foreground start. | Signed proof recorded 1.025s and 1.048s of background bootstrap; the subsequent `container start` completed in 0.10s and 0.13s while reusing the prepared helper. | No Apple PR. The related [apple/container #1924](https://github.com/apple/container/issues/1924) is an open request for a pre-warmed micro-VM pool. |
| Prewarm eligibility guardrail | [container #179](https://github.com/stephenlclarke/container/pull/179) excludes block-backed mounts from background prewarming because speculative ownership can prevent another container from using a shared volume. | Focused eligibility and reproduction evidence show that correctness wins over speculative warm-start latency for block-backed mounts; VirtioFS-only eligible workloads keep the optimization. | Not an optimization to propose independently; it is a required safety boundary for prewarming. |
| Live memory resize | [container #154](https://github.com/stephenlclarke/container/pull/154), built on Containerization memory controls, adds live workload-memory targets while keeping the VM boot maximum available for restoration. | A live 256 MiB resize completed in 30 ms and asynchronous reclamation shed 294,800 KiB of host RSS (17.4%) without an OOM or workload restart. | No Apple PR. [apple/container #1867](https://github.com/apple/container/issues/1867) is an open request for dynamic resource reallocation; [apple/containerization #893](https://github.com/apple/containerization/pull/893) was a related stock-Apple memory-balloon PR that closed without merge. |
| Adaptive memory reclamation | [container #158](https://github.com/stephenlclarke/container/pull/158) adds an opt-in, hysteresis- and cooldown-controlled dedicated-VM policy that lowers the live target only after sustained low demand and restores it under pressure. | Release proof shows a 2 GiB VM reaching the configured 256 MiB floor, returning to its 2 GiB maximum under demand, and avoiding OOM kills. | No Apple PR. Discuss after agreeing on the lower-level balloon mechanism and ownership model. |

### 4. Invocation and release-path work

These changes are part of the 0.14.0 optimization set but are not natural Apple upstream handoffs because they belong to Compose or to its release process.

| Change | What changed | Evidence and boundary |
| --- | --- | --- |
| Invocation-scoped Container client | [container-compose #327](https://github.com/stephenlclarke/container-compose/pull/327) lazily constructs one control-plane client per Compose invocation and keeps attach and exec clients separate because their disconnect closes the underlying XPC connection. | This reduces repeated XPC client construction, but its retained startup and teardown evidence was mixed; it deliberately makes no independent latency-improvement claim. |

| Release critical path | [container-compose #322](https://github.com/stephenlclarke/container-compose/pull/322) parallelizes independent DocC work, moves demo recording out of package publication, and reuses a verified runtime candidate instead of rebuilding sibling source. | This improves release throughput, not Container runtime behavior, and has no Apple repository target. |
| Integration and measurement | [container-compose #325](https://github.com/stephenlclarke/container-compose/pull/325) pins the optimized stack; [#331](https://github.com/stephenlclarke/container-compose/pull/331) adds the isolation matrix; [#338](https://github.com/stephenlclarke/container-compose/pull/338) removes competing runtime workers from release measurements. | These provide integration and measurement integrity, not a separate product-runtime optimization. |

### 5. Concurrency safety work that limits the claims

Two Containerization changes in the exact source range support safe parallel execution but have no standalone speed claim: [containerization #48](https://github.com/stephenlclarke/containerization/pull/48) isolates concurrent Netlink sessions, and [#50](https://github.com/stephenlclarke/containerization/pull/50) tolerates concurrent mountpoint creation. They should travel with a concurrency discussion as correctness prerequisites, not as measured wins.

## What the release evidence proves

The [historical release-artifact matrix](benchmarks/0.14.0-vs-0.13.0.md) ran five counterbalanced repetitions per lane on the same host. Its strongest combined-release improvements were Docker-normalized median reductions of:

- 72.2% for 10-service startup and 72.3% for 50-service startup;
- 64.7% for 10-service logging aggregation; and
- 66.1% for time to first logging output.

The result is not universally better. It also reports a Docker-normalized 18.8% regression for one-service startup, a 19.9% regression for one-service logging aggregation, and regressions for JSON-compression and local-rotation logging writes. That is the appropriate boundary for an Apple conversation: the evidence supports specific warm-image, multi-service lifecycle and logging fixtures, not a general "0.14.0 is faster" claim.

Additional focused proof is available in the linked support-fork pull requests:

- [container #142](https://github.com/stephenlclarke/container/pull/142) and [containerization #37](https://github.com/stephenlclarke/containerization/pull/37) completed 84 baseline and 84 candidate operations and reported 1.5% to 28.6% combined-stack lifecycle-median gains; neither assigns those gains to an individual commit.
- [container #143](https://github.com/stephenlclarke/container/pull/143) and [#145](https://github.com/stephenlclarke/container/pull/145) provide the controlled bootstrap-scaling numbers above.
- [container #150](https://github.com/stephenlclarke/container/pull/150), [#154](https://github.com/stephenlclarke/container/pull/154), and [#158](https://github.com/stephenlclarke/container/pull/158) provide signed warm-start and memory-control proofs.
- [builder-shim #12](https://github.com/stephenlclarke/container-builder-shim/pull/12) proves cache-hit, cache-miss, completion-marker, invalid-input, and legacy-transfer behavior, but has no isolated throughput percentage.

The release comparison's raw data, JUnit, timing matrices, and fingerprints are retained by its [workflow artifact](https://github.com/stephenlclarke/container-compose/actions/runs/33468711244).

## Recommended Apple discussion order

1. Agree on a reproducible benchmark contract using [apple/containerization #729](https://github.com/apple/containerization/issues/729), including the multi-service startup and time-to-first-output fixtures used here.
2. Walk the small, additive cached-context protocol first. It has the narrowest API surface and a complete compatibility story in [builder-shim #12](https://github.com/stephenlclarke/container-builder-shim/pull/12).
3. Split the two large local Apple-shaped series into reviewable themes: event-loop sizing, lock scope and lifecycle preparation, image/archive work, and readiness/cancellation. Do not propose the 48 commits as one opaque PR.
4. Discuss bounded bootstrap admission next, using its 50-service median and P95 evidence. It has a narrow safety policy and clearer attributable results than the broad stack benchmark.
5. Treat prewarming, live resource control, and shared VM execution as separate architecture proposals. They have meaningful isolation, ownership, recovery, and public-API consequences even when their latency or memory results are promising.

No Apple issue, pull request, branch, or push is created by this document.
