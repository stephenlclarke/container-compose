# PR 678: recover cleaned release checkpoints

## Summary

- Normalize retry-scoped signing-keychain and GitHub handoff destinations out
  of the release environment fingerprint while retaining the exact signing
  identity as a result-bearing input.
- Add an opt-in, reuse-only recovery pass after a successful checkpoint leaves
  a descendant that the existing bounded supervisor cleans up.
- Refuse to execute the stage during recovery and retain hard failures for
  every timeout, failed stage, invalid checkpoint, changed input, and repeated
  process leak.
- Record successful post-exit cleanup recovery in the durable checkpoint
  evidence.

## Motivation and context

Unattended 0.15.2 promotion
[34862188599](https://github.com/stephenlclarke/container-compose/actions/runs/34862188599)
completed the full `sibling-stack` stage, including 309 concurrent tests, 100
serial live integration tests, and combined coverage. The nested supervisor
then cleaned one Xcode Python descendant after the configured 30-second drain
and returned exit 125. A workflow retry could not reuse the status-0 checkpoint
because its temporary Developer ID keychain and GitHub output paths changed the
otherwise identical environment fingerprint.

This correction keeps the generic supervisor fail closed. Only checkpointed
release invocations opt into one recovery pass, and that pass starts a newly
supervised worker in reuse-only mode. It recomputes the complete input
fingerprint and validates the retained log and required products. If exact
reuse is unavailable, it returns a distinct failure without invoking the stage
command.

## Docker Compose parity

This change affects release-process recovery only. It does not change Compose
parsing, runtime behavior, Docker Compose parity observations, package bytes,
or supported commands. The successful runtime proof from the failed promotion
remains retained, while the reviewed controller tree will produce its own
exact release authority.

## Compatibility impact

None. The generic command supervisor and checkpoint controller retain their
fail-closed defaults. Release-gate stages opt into bounded recovery only when a
status-0 exact-input checkpoint has already been written and its complete
worker session has been cleaned.

## Remaining risks

The retained 0.15.2 transaction must complete publication after this correction
reaches `main`. A changed reviewed tree will intentionally invalidate earlier
tool fingerprints while equivalent workflow retries will retain one
environment identity.
