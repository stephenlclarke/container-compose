# Pull request 646: stage Bridge transformer output internally

Pull request [#646](https://github.com/stephenlclarke/container-compose/pull/646) implements issue [#645](https://github.com/stephenlclarke/container-compose/issues/645).

## Summary

- Stage the transformer's `/out` bind beside the existing runtime-safe Bridge input.
- Publish completed output to the requested directory only after every transformation succeeds.
- Preserve hidden and nested artifacts, output confirmation, replacement, and permissions.
- Remove staging after both successful and failed transformations.

See the companion [issue handoff](ISSUE-645.md).

## Motivation and context

Virtualization.framework blocked while opening an external APFS output directory as part of a `VZMultipleDirectoryShare`. The transformer guest never booted and the 0.15.0 parity gate timed out after 900 seconds. Bridge input was already private and runtime-safe, so making output follow the same mount boundary avoids the host privacy and removable-volume failure without changing the user-selected destination or introducing Docker into the runtime.

## Implementation

- `ComposeOrchestrator.bridgeConvert` creates a private output staging directory next to its generated input, mounts that directory at `/out`, and publishes it only after all transformer invocations finish.
- `publishBridgeOutputDirectory` copies each direct staged entry so nested directories and dotfiles are retained.
- The Bridge test runner materializes simulated transformer output in the actual `/out` mount.
- Regression tests prove staging and cleanup, successful nested and hidden publication, no publication after transformer failure, comma-containing output and template paths, and existing output semantics.

## Compatibility and risk

Stock and enhanced profiles use the same runtime-neutral Bridge orchestration. The transformer image, arguments, input model, template mounts, generated tree, and final output path are unchanged. Output remains empty if a transformation fails, and private staging is removed on every terminal path. Conversion without an output directory and dry-run behavior are unchanged.

The final publication copies from the internal runtime volume to the requested destination after transformation. Its cost is proportional to generated output size and occurs outside the guest startup boundary; ordinary timing differences remain diagnostic unless a run hangs, fails to complete, or becomes at least an order of magnitude slower.
