# PR 682: isolate signing state in release-policy tests

## Summary

- Remove inherited signing identity and Keychain variables from the shared non-interactive release-test environment.
- Clear the inherited Keychain explicitly in the hosted stack-validation fixture before exercising missing-signing guards.
- Extend the environment-isolation regression to cover both signing variables.

- [x] Bug fix
- [ ] New feature
- [ ] Breaking change
- [x] Documentation update

## Motivation and context

Scheduled stable release run [34896635604](https://github.com/stephenlclarke/container-compose/actions/runs/34896635604) correctly installed and exported its operation-scoped Developer ID Keychain. After the 5,226.760-second sibling-stack checkpoint passed, the release-tool suite inherited that Keychain in two tests whose purpose is to verify missing-Keychain failure paths. The full 643-test suite reported exactly those two failures after 728.318 seconds.

The test harness already strips recursive Make and release-dispatch state. Signing identity and Keychain state are equally parent-owned inputs and must be opt-in per fixture. Clearing them at the shared boundary makes policy tests deterministic both on a developer shell and inside the real unattended signing workflow. The hosted-stack test constructs its own environment directly, so it also clears the Keychain before its missing-signing assertions.

## Docker Compose parity

This change affects test process environment isolation only. It does not change Compose parsing, Engine behavior, Docker Compose parity fixtures, supported commands, or runtime packages.

## Compatibility impact

There is no user-visible compatibility change. Tests that need signing state must continue to configure their own explicit fixture identity and Keychain, which matches the existing release security contract.

## Remaining risks

The complete release-tool suite and the resumed stable promotion must prove that no other policy test depended accidentally on parent signing state. The exact sibling-stack checkpoint is retained and should be reused only while its immutable fingerprint remains unchanged.
