## Motivation and Context

The parity design set names more than one hundred implementation checkpoints,
but their numbering is local to each document and their state is prose. A later
slice can currently remove a row, reuse an ID, leave a generated summary stale,
or call work complete without immutable evidence and complete documentation
review. That makes the broad multi-repository waves unsafe to resume or audit.

## Design choices and compatibility

- Keep the JSON register as the sole state source and generate its Markdown
  reader deterministically. Human-authored design prose and acceptance
  conditions remain in their focused authorities.
- Use globally unique uppercase IDs whose lowercase spelling is the explicit
  HTML anchor in the design. The checker requires the visible ID within 300
  characters of that anchor and requires a one-to-one register mapping. An
  independent reviewed contract pins the programme root plus all 112 IDs,
  design paths, kinds, prefixes, repository sets, item overrides, and
  documentation dependencies so moving the baseline or deleting a requirement
  from both sources cannot silently redefine scope.
- Partition IDs into `not started`, `in progress`, `blocked`, or `verified`.
  Duplicate state membership or evidence for a non-verified row fails.
- Require blocked rows to carry owner, blocker, next action, and review date.
- Accept `verified` only with a full existing Container Compose commit that is
  an ancestor of both the checkout and the trusted pre-change main/PR-base
  checkpoint, a matching Compose repository head, safe evidence paths present
  in that exact tree, at least one durable authority, and same-head
  dispositions covering every documentation dependency declared by the
  design. Pull-request CI supplies its immutable base SHA, while local runs
  default to the local `main` ref, so a commit introduced in the current pull
  request cannot declare itself or a sibling PR commit accepted.
- Resolve every matched repository through a fixed Container-family checkout,
  require one checkout remote to identify the exact GitHub repository, and use
  hardened Git object reads there. Every recorded SHA must resolve to itself as
  a commit object rather than merely peel from an annotated tag, and the commit
  must be contained in fetched `main` for that identified remote. A missing
  checkout, fabricated hash, indirect tag object, unmerged commit, object from
  a differently named repository, or unavailable historic object fails.
  Both hosted validation paths fetch full Container, Containerization,
  container-builder-shim, container-k8s, and Homebrew-tap histories for this
  evidence check. The generated reader exposes each design default and item
  override as well as the heads, paths, rationales, and authorities.
- Require every design to declare a sorted default repository set and explicit
  item overrides. These sets are independently pinned with the design/ID
  contract. A verified row must supply exactly its inherited or overridden set;
  omitting an affected repository or adding an undeclared repository fails.
- Run exact Git queries through `/usr/bin/git` with replacement objects and
  ambient Git/configuration controls disabled. The lightweight CI checkout uses
  full history and invokes the focused gate, so a state-only documentation PR
  cannot bypass it.
- Treat authority URLs as executable evidence contracts rather than arbitrary
  HTTPS links. Only kind-specific GitHub pull requests/comments, Actions runs,
  and commit deliveries in an affected repository are accepted. The fixed
  system GitHub CLI runs with a bounded clean environment and timeout and must
  prove remote resources exist; pull requests must be merged to the accepted
  head, quality/test runs must have completed
  successfully at that head, and commit URLs must equal an authenticated
  repository head. Hosted source-check steps receive only the read-only
  workflow token needed for those API reads. The workflow-level permission set
  explicitly grants `actions: read` while retaining no write permission, so
  GitHub's unspecified-permissions-to-none rule cannot block Actions evidence.
- Leave this slice's own `WORKFLOW-ENABLER-15` row `in progress`. A subsequent
  reviewed checkpoint will point it to this slice's already-existing merge,
  avoiding an impossible self-referential commit hash or a floating alias.
- Keep detailed STATUS/capability requirement manifest work in
  `CLOSURE-R0`; this slice supplies its stable progress-control prerequisite but
  does not claim that oracle reconciliation is complete.
- Change no Compose runtime behavior, dependency revision, release artifact, or
  performance gate. Executable performance is not applicable.

## Remaining risks

The first accepted-head record for Enabler 15 necessarily lands in the next
reviewed checkpoint. Until then its state is truthfully `in progress`; all
delivered validation behavior is nevertheless active. Historical evidence is
limited to direct repository commit objects and durable, API-verifiable GitHub
authorities. A transient GitHub API/authentication failure fails the progress
gate rather than treating an unverified link as evidence. The
later shared slice-ledger enabler will broaden cross-repository evidence layout
without weakening this register.
