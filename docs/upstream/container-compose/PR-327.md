# Pull request 327: reuse the invocation Container client

## Summary

- Lazily construct one control-plane `ContainerClient` for a Compose invocation.
- Share that client across discovery, lifecycle, events, logs, stats, top, and
  filesystem control calls.
- Keep attach and exec sessions on dedicated clients because their disconnect
  operation owns and closes the underlying XPC connection.
- Preserve public dependency construction and help or parser-only laziness.

Pull request:
[`#327`](https://github.com/stephenlclarke/container-compose/pull/327).
Tracking issue:
[`#278`](https://github.com/stephenlclarke/container-compose/issues/278).

## Implementation

`InvocationScopedValue` provides mutex-protected, exactly-once lazy
construction. `InvocationScopedClientPool` separates the shared control value
from fresh connection-owned session values. The Compose runtime composition
root injects those providers into each direct Container API adapter rather
than constructing clients inside individual calls.

The separation is required because `ClientProcess.disconnect()` closes its
underlying XPC connection. Sharing an attach or exec session client with
ordinary control traffic would allow session teardown to interrupt unrelated
work.

## Matched release benchmark

The candidate was built in release mode against the same Container
`731f195c3f800a451d4026f29985e69367899d79` and Containerization
`97049499f98dd0a34dac2001045a3c6009088a04` source revisions as the retained
baseline. All timed binaries, fixtures, images, kernel, configuration, and
evidence lived on internal storage under a marker-protected `/private/tmp`
root. Seven counterbalanced repetitions produced 84 successful operations,
functional parity PASS, and the diagnostic 10x guard PASS.

Median changes against the retained evidence were:

- startup at 1, 10, and 50 services: -5.3%, +10.0%, and +13.2%;
- teardown at 1, 10, and 50 services: +5.2%, -1.5%, and -1.9%.

The latency evidence is mixed. This pull request therefore claims reduced XPC
client construction and clearer connection ownership, not a startup or
teardown latency improvement.

## Compatibility and remaining scope

The two public `ComposeContainerRuntime.dependencies` call shapes are retained.
No XPC connection is opened by parser or help-only paths. Session cancellation
and disconnect ownership remain isolated.

Issue 278 remains open. Explicit `shared-vm` and `dedicated-vm` isolation,
dedicated-path pre-warming, and the remaining CPU, RSS, I/O, attach, logging,
provider, watch, and build-context lanes are separate work packages.
