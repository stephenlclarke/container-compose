# PR 676: propagate the release-checkpoint drain

## Summary

- Add a validated natural-drain option to the nested release-checkpoint
  controller.
- Forward the selected value to the process-group supervisor that owns the
  checkpoint worker session.
- Give only the expensive `sibling-stack` release checkpoint the existing
  30-second teardown allowance.
- Make the tracked-source mutation regression independent of macOS `/var` to
  `/private/var` path canonicalization.

## Type of change

- [x] Bug fix
- [ ] New feature
- [ ] Breaking change
- [x] Documentation update

## Motivation and context

Unattended 0.15.2 promotion
[34843652063](https://github.com/stephenlclarke/container-compose/actions/runs/34843652063)
completed the full `sibling-stack` checkpoint successfully: 309 concurrent and
100 serial live integration tests passed, coverage export completed, and the
checkpoint recorded status 0. The nested deadline supervisor then used its
unchanged five-second default, found a still-draining Apple/Xcode descendant,
cleaned it, and returned exit 125.

Pull request 675 correctly gave the outer release transaction 30 seconds, but
that setting could not reach the independent supervisor constructed inside
`run-release-checkpoint.py`. This change propagates the bound across the actual
nested supervision boundary while preserving fail-closed leak detection.

## Docker Compose parity

This change affects release-process supervision only. It does not change
Compose parsing, runtime behavior, Docker Compose parity observations, package
bytes, or supported commands. The successful runtime checkpoint from the
failed promotion is retained as failure evidence, but the changed reviewed tree
must produce fresh release evidence.

## Compatibility impact

None. The checkpoint controller retains its five-second default. Only the
release gate's `sibling-stack` invocation selects 30 seconds. Persistent
descendants remain a hard failure and are terminated by the existing bounded
cleanup path.

## Remaining risks

The retained 0.15.2 transaction must complete a fresh exact-tree release gate
and publication after this correction reaches `main`.
