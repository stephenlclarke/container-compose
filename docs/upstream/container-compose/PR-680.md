# PR 680: bind unattended signing to the operation Keychain

## Summary

- Validate and canonicalise the operation-scoped Developer ID Keychain before release-owned Container source builds.
- Pass the exact Keychain to runtime-candidate packaging, direct Container builds, and independently checkpointed Container validation targets.
- Reject missing, relative, shell-unsafe, non-regular, and symlinked Keychain paths before expensive work begins.

## Motivation and context

Unattended 0.15.2 stable release run [34884902647](https://github.com/stephenlclarke/container-compose/actions/runs/34884902647) stopped making progress while a nested Container build signed its executable. Process sampling showed `codesign` blocked in SecurityServer signature generation. The release controller had installed, unlocked, partition-authorised, and preflighted its temporary Developer ID Keychain, but the nested command carried only the certificate fingerprint. Because the host has duplicate copies of the same identity, macOS could select a login-Keychain private key and wait for account authentication.

The correction keeps the existing certificate fingerprint as the result-bearing checkpoint input while treating the workflow-attempt Keychain filename as retry metadata. Each signing path validates the configured file, canonicalises its parent, and supplies `--keychain` before `--sign`. No Keychain contents, passwords, identities beyond the public fingerprint, or other secret material enter logs or retained evidence.

## Docker Compose parity

This fix changes release orchestration only. It does not change Compose parsing, Engine behavior, Docker Compose parity, runtime packages, or supported commands. Previously completed exact-input checkpoints remain reusable because the signing identity has not changed and operation-scoped Keychain destinations are intentionally normalised from the inherited environment fingerprint.

## Compatibility impact

Ordinary product behavior and manual package signing are unchanged. Full release-owned stack validation already requires a Developer ID identity for unattended source-runtime tests; it now also requires the operation-scoped Keychain containing that identity. The scheduled stable-release workflow has supplied that Keychain since the unattended signing flow was introduced.

## Remaining risks

The retained 0.15.2 release transaction must be restarted from the reviewed `main` correction and prove real signing plus publication on the self-hosted runner. Any further nested signing path that discards `CODESIGN_OPTS` will fail the exact production proof rather than being inferred as correct.
